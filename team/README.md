# Team handbook

Internal. Not published, not pasted to customers.

## Read in this order

**Day one:** everything in [`onboarding/`](onboarding/).

**Then, with the queue open:** [`workflows/`](workflows/) for how a ticket
moves, [`playbooks/`](playbooks/) for the situations that come up repeatedly,
[`macros/`](macros/) for text you can start from.

**When you need a number:** [`reference/`](reference/).

## The three things that matter most

1. **[What we have not built](reference/not-built-yet.md).** Read it before
   you answer anything about domains, uptime, crash alerts or teams. The
   marketing site is ahead of the product and repeating it turns a
   disappointment into a lie.

2. **Nobody is in trouble for saying "I do not know, let me find out."** They
   are in trouble for guessing at a customer.

3. **`waiting` stops the SLA clock.** Use it when the ball is genuinely with
   the customer. Do not use it to make the queue look better.

## What support can and cannot do

| | Support | Manager | Admin |
| --- | --- | --- | --- |
| Read tickets, reply, note | yes | yes | yes |
| See a customer's server | yes | yes | yes |
| Assign, re-prioritise, triage | no | yes | yes |
| Restart / suspend a server | no | yes | yes |
| Read billing | no | yes | yes |
| Change billing, comp a plan | no | no | yes |
| Change roles | no | no | yes |
| Raise an account's limits | no | no | yes |

If you need something above your line, ask — do not find a way around it.
Every staff action is written to the customer's activity log with your name on
it, and they can read it.

## Tone, in one line

Plain, specific, and on their side. Never blame the customer, never blame a
colleague in writing, and never say "unfortunately".
